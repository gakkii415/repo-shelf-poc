# AI投稿手順

## 次のAIへ渡す指示

対象リポジトリは `gakkii415/repo-shelf-poc`。`AGENTS.md`、この文書、`article.schema.json`、`content/articles/ripgrep.json` を読んでください。GitHubリポジトリの紹介記事を、指定された件数だけ追加してください。

最初に既存の記事を確認し、紹介済みのリポジトリを除外した候補一覧を決めてください。記事のテーマだけでなく紹介先の `owner/name` も重複させません。コードやデザイン、スキーマは記事追加のために変更しません。

公式README・公式ドキュメントを確認して記事を執筆し、出典と実際の確認日を記録してください。GitHubのURLを作れたことと、実在・内容を確認できたことは別です。未確認の記事は公開しません。スター数・最新バージョン・ライセンスなど変化する情報は、確認できた場合だけ本文で出典と確認日を伴って扱ってください。

1記事を `content/articles/<slug>.json` に保存します。本文はプレーンテキストです。HTMLと山括弧は禁止、Markdown記法はそのまま表示されます。見出し・段落・箇条書きには構造化フィールドを使用します。

## バッチと並列作業

- 推奨開始値は5〜10記事を1バッチ。これは品質を保証する値ではなく、失敗時の修正範囲を限定する運用単位です。
- 最初の5記事をレビューした後、残りを複数バッチに分割します。30〜100記事を1つの巨大JSON配列にまとめません。
- 複数エージェントは担当するリポジトリ一覧を分担し、それぞれ独立ファイルを作ります。親は最新mainに各バッチを統合して、全体の重複検査を再実行します。
- 編集担当とは別のレビュー担当が、公式出典との整合性、説明の有用性、重複を確認します。
- 最終的な目標は依頼件数の記事追加です。検査に合格させるために記事を黙って削除したり、スキーマを緩和したりしません。

## JSONの必須フィールド

| キー | 値 |
| --- | --- |
| schemaVersion | `1` |
| slug | 英小文字・数字・ハイフン。ファイル名と一致 |
| title / summary | タイトル、短い紹介。最大120 / 400文字 |
| repository | `owner/name` |
| category | `ai`, `frontend`, `backend`, `developer-tools`, `data`, `automation` |
| tags | 1〜8個、1個40文字以内 |
| publishedAt / verifiedAt | 実在する日付 `YYYY-MM-DD` |
| status | `published` または `draft` |
| sections | `{heading, paragraphs, bullets?}` の配列 |
| sources | `{label, url}` の配列。公式GitHubリポジトリURLを含む |

`publishedAt` は表示日であり、予約投稿機能ではありません。`published` は未来の日付でもビルド時に掲載されます。更新は同じファイル・slugを使用します。URLが変わるので、公開後にslugを変更しないでください。

## 投稿と確認

1. `content/<batch-name>` の作業ブランチを最新mainから作成。
2. JSONを追加し、実行環境があれば `npm run check` を実行。
3. Pull Requestを作成。実行環境がなくてもGitHub Actionsが検査します。
4. エラーに表示されたファイル名・フィールドを修正。CIの `validate` 成功と記事レビューを確認してからマージ。
5. mainの `Validate and publish articles` が配信まで成功したことを確認。
6. 公開サイトの `catalog.json` と追加した記事のURLで件数と反映を確認。報告には作成数、既存を含む総数、失敗・未確認数、PRと公開URLを記載。

検査エラーはビルド全体を停止します。不正JSON、必須項目漏れ、未知のフィールド、同じリポジトリ・slugの重複、不正な日付、HTML、危険なURLなどが対象です。出典のURL先へのアクセスや事実確認は、執筆・レビュー担当が行います。

## 戻し方

問題のあるバッチを追加したPRの変更をrevertし、その修正をmainへマージします。再ビルドで該当記事が削除され、前の有効な内容が反映されます。既存ファイル全削除や履歴の強制上書きはしません。

## PoCで記録するもの

依頼件数、初回合格件数、修正件数、最終掲載件数、重複・事実誤りの件数、各バッチの所要時間。合成データによる `npm run benchmark` は配信基盤の容量検証であり、AIの執筆品質検証とは区別します。
